# TrackBox24 Web

Бек-офіс [TrackBox24](https://trackbox24.com): посилки, клієнти, рейси, склади, оплата, користувачі компанії. Сканування (отримання з НП, завантаження, видача, на склад) — у мобільному застосунку, у вебі його немає.

**Стек:** React 19, Vite, TypeScript, Tailwind v4 + shadcn/ui (Base UI), react-router, TanStack Query, react-hook-form + zod, react-i18next (поки лише `uk`), openapi-fetch з типами, згенерованими з OpenAPI бекенду.

## Запуск

Потрібен запущений бекенд (`trackbox24_back`, `docker compose up -d --build`) на `http://localhost:8080` — у dev-режимі Vite проксує `/api` туди, бо CORS на бекенді не налаштований. На проді веб і API мають бути на одному origin за reverse-proxy.

```bash
npm install
npm run dev            # http://localhost:5173
```

Тестові облікові записи після сіду e2e: `admin@trackbox24.com` / `admin12345` (ADMIN), `manager@test.ua` / `manager123` (MANAGER).

## Ролі у вебі

| Роль | Що бачить |
|---|---|
| `MANAGER` | усе в межах своєї компанії: посилки, клієнти, рейси, склади, користувачі, машини, «Компанія», «Кошик»; усі дії |
| `VIEWER` | ті самі екрани без кнопок дій (включно з грошима) |
| `ADMIN` | компанії та їхні користувачі; з картки компанії «Відкрити компанію» → ті самі екрани менеджера **лише для читання** (запити йдуть із заголовком `X-Company-Id`); банер зверху, «Вийти з режиму» |
| `SALES` | команда TrackBox24 (продажі й підтримка): CRM — угоди, задачі, команда; компанії-клієнти й перемикачі їхніх опцій (фото, публічне відстеження); без посилок і клієнтів перевізників, без «Відкрити компанію» і користувачів компаній |
| `REPRESENTATIVE` / `DRIVER` (без інших ролей) | сторінка «користуйтесь мобільним застосунком» |
| гість | лендінг на `/` (продаюча сторінка з презентації), вхід на `/login` |

У користувача може бути кілька ролей; права — об'єднання. Логіка в `src/features/auth/access.ts` (`useAccess`: `canEdit`, `canSeeMoney`, `companyMode`…).

## E2E

`e2e/` — шість сценаріїв на Playwright (посилки+клієнти+склади+оплата; адмін+користувачі+машини+VIEWER; рейси; відправка НП; фото посилок; публічне відстеження), без тест-раннера: кожен крок друкує `PASS`/`FAIL`, процес завершується з кодом 1, якщо щось впало. Потрібні запущені `npm run dev` і бекенд; фікстури створюються автоматично, а відкриті рейси з попередніх прогонів сід скасовує (селект рейсів бере лише перші сто). Скани водія емулюються прямими викликами `POST /api/scan/load|deliver`. Адреси можна перевизначити через `E2E_BASE_URL` / `E2E_API_URL`.

## Нюанси бекенду, на які спирається фронт

- **Фото посилок** (`ParcelPhotosCard`): до 3 фото на посилку, `GET/POST/DELETE /api/parcels/{id}/photos`. Файли йдуть одним `multipart` як є (HEIC теж) — конвертує сервер, усі або жодного. Посилання presigned і живуть годину: помилка завантаження `<img>` → перезапит списку. Увімкнення — `photosEnabled` компанії (`PUT /api/companies/{id}/photos`, лише ADMIN; перемикач у реквізитах компанії); без нього картка показується лише коли фото вже є, без кнопки додавання. Фото виданих посилок сервер видаляє через 14 днів.
- **Оплати** (`features/billing`): усе під `/api/crm/prices|invoices|companies/{id}/billing`. Суми в EUR, рядки рахунку — дні з
  місяця за ціною на момент формування. Компанія з `suspended` (прострочка понад 14 днів) — червоний бейдж і рядок у списку; її
  користувачі на вході отримують 403 з поясненням — `LoginPage` показує `detail`. Перемикачі опцій компанії оновлюють і дані оплати.
- **Переїзди** — посилки з `kind: MOVE`: список посилок їх не показує (`kind=PARCEL`), у них свій розділ. Місця: `PUT/POST /api/parcels/{id}/seats…`, перевірка `GET/POST …/seats/check`, реєстр `…/seats/register.xlsx`, фото місця `POST …/photos?seatNumber=N` (картка «Фото» показує лише фото всієї посилки).
- **Публічне відстеження** (`/track`, `/track/{код}`, без входу): `GET /api/public/tracking/{код}` — наш `PT0123456789`, місце `PT0123456789-2` або 14 цифр ТТН НП; пробіли й регістр прибираємо самі, явно хибний формат відповідаємо без запиту. Бек рахує невдалі пошуки з однієї адреси (30 за 15 хв → 429), тому запит не повторюємо ні автоматично, ні при фокусі вікна; 404 і 429 показуємо `detail` як є. Показуємо `statusLabel` і `history[].label` (слова для клієнта), не наші назви статусів. Орієнтовна доставка — `expectedDeliveryOn` з підписом за `expectedDeliverySource` (план рейсу чи прогноз НП); без неї — `expectedArrivalAt`, як було. Посилання для поширення — `trackingUrl` у посилці («Копіювати посилання» в картці); порожнє — у компанії вимкнено опцію `publicTrackingEnabled`, кнопки немає.


- JWT без refresh-токена (TTL 12 год); токен відкликається при зміні пароля/ролей/деактивації — на 401 клієнт чистить токен і веде на `/login?reason=expired`. `POST /api/auth/password` повертає новий токен, який підміняється без перелогіну.
- Рейс: `PLANNED → PREPARING → IN_PROGRESS → COMPLETED | CANCELLED`. План — лише для менеджера; у машину посилки потрапляють сканами з `tripId`. При виїзді незавантажене знімається з плану. `complete` відповідає 409 з `undeliveredParcels`, якщо в машині ще є посилки — веб пропонує перемістити їх на склад і повторює.
- `GET /api/trips/{id}/parcels` — план і факт в одному списку: `plannedTripId` / `tripId`; прогрес — за `seats[].status`.
- Склади: `POST /api/warehouses/{id}/parcels` — all-or-nothing; ручний статус `AT_WAREHOUSE` вимагає `warehouseId`.
- Ціну доставки та оплату бачать усі, крім чистого REPRESENTATIVE; змінює лише MANAGER.
- Зворотні посилки: `PUT /api/parcels/{id}/np-shipment` **замінює всі поля** відправки (форма надсилається цілком) і працює, поки посилка в нас (`RECEIVED_BY_REPRESENTATIVE`, `ACCEPTED_BY_DRIVER`, `AT_WAREHOUSE`, `IN_CAR`); ЕН створює водій при прийомі (у мобільному) або менеджер тут (`POST …/np-shipment/waybill`), доки її не прийняла НП — видаляє (`DELETE …/waybill`). Неповні дані → 400 зі списком, що заповнити; показуємо як є. Тип вантажу стоїть першим у діалозі, бо задає правила: «Документи» їдуть без ваги (бек надсилає 0,1 / 0,5 / 1 кг і не передає габарити, вага > 1 кг — помилка форми), посилка й вантаж без ваги ЕН не отримають. Опис до 500 символів, габарити 0,1–9999 см. У відповіді `shipDate` — дата відправки в ЕН (планове прибуття рейсу + 1 день). ЕН, видалену в кабінеті НП, синхронізація сама знімає з посилки; `DELETE /api/parcels/{id}` видаляє і ЕН (діалог підтвердження про це попереджає), а вже передану в НП посилку видалити не дає. Далі статуси ставить синхронізація: `SENT_VIA_NOVA_POSHTA`, потім `DELIVERED_TO_CLIENT`.
- Оплата при прийомі: `POST /api/parcels` з `paymentMethod` (`CASH` / `UA_CARD` / `FOREIGN_CARD`) створює посилку одразу оплаченою (потрібна ціна). У формі створення — «Оплачено зараз» поруч із ціною, лише для менеджера.
- Етикетки (`/parcels/:id/labels`): формат «На принтер (100 мм)» або «Етикетка 70×40 мм» для стрічкового NIIMBOT B3S (`?size=70x40`, `@page 70mm 40mm`). На малій етикетці два Code 128 — наша ЕН (якщо створена) і `PT…`/`PT…-N` місця, між ними отримувач, місто, відділення, «N/всього» і вага. Після створення ЕН етикетку передруковують.
- Довідники НП (`/api/nova-poshta/cities|warehouses|streets`) ходять у НП живим запитом ключем компанії: без ключа — 400, НП недоступна — 502; пікери показують цей текст замість порожнього списку. НП обмежує частоту запитів, тому пошук іде через 400 мс після останньої літери, а не на кожну. Зберігаємо і `ref`, і назву.
- `PUT /parcels/{id}` — часткове оновлення (пропущене не змінюється). Габарити (`lengthCm/widthCm/heightCm`) і місто доставки (`deliveryCity`, порожнє = місто клієнта) вводяться вручну, НП їх не віддає; `npVolumeWeight` — лише з НП.
- Усі списки сторінками, зокрема історії й посилки рейсу (`{content, page}`); веб бере історію/посилки рейсу з `size=200`.
- М'яке видалення: `DELETE /api/<сутність>/{id}` + `POST …/restore`, кошик `GET …/deleted`; правила «коли можна видалити» — на бекенді, веб показує `detail` помилки.
- `GET /api/trips` віддає лічильники `plannedCount/loadedCount/deliveredCount`, фільтри `status` (кілька) і `open=true`; `GET /api/trips/{id}/register.xlsx` — реєстр рейсу.
- Усі поля відповідей опціональні (`null` пропускається), помилки — RFC 7807 з мапою `errors` для валідації.
